# 2026年10月15〜16日 BS2K対応試行の記録（公開版）

私的な接続設定、個別予約やファイル名、放送データ、メモリdump、CAS応答を除いて、元の開発記録から技術的な経緯を整理した。失敗した仮説と後で訂正した成功判定を残す。最新の開発基準は`ccf4332`であり、午前の修正版`44f1959`より後の取得済み4Kパッケージ確認を含む。

## 出発点と調査方針

本家mkraでBS4Kの選局とMMT→TS配信が動いていた。通常BSも同じAPIで局番号を変えればよいのでは、という問いから調査を始めた。しかしSC1501AのISDB-Sロック、TSの電気出力、XCode6入力、DEMUX、CASは別の層だった。

SC1501Aのメーカー仕様はISDB-SとISDB-S3を含む。通常BSのTS出力能力は基板上の経路・ファーム制御までの証明ではない。SC1502A等の類似ICのピン配置・レジスタはそのまま流用しない。SC1501Aと呼ばれたLinux driverに別ICとの混同訂正がある点にも注意した。

SHARP/MASPROの更新RVPには約67.49MBの連続一致領域と134,992バイトの共通末尾があったが、高エントロピーのpayloadからTSI設定は取り出せなかった。当初受領したI-O DATA EXEは途中切れだったが、その後公式から74,017,792Bの完全版を取得し、3社すべてのRVPで同じ主要領域と末尾を確認した。初版公開の要約ではこの後半を落としていたため訂正する。[3社比較の範囲・ハッシュ・展開警告](OEM-FIRMWARE-COMPARISON.ja.md)を参照。共通領域を同じ実行コードや他機種の動作保証とは扱わず、他社firmwareの実行・書込みはしていない。

## 1. 通常BS選局API

純正4Kの`Tune_ISDB_S3_SetTsid`相当のログと、通常BSのlegacy FEM/FED経路を比較した。単純に4KのSIDを通常BSへ変えるだけでは入力・TS取得まで切り替わらなかった。

直接の復調設定、FEM経由、TSID指定、相対TS番号指定、TMCC確認を比較した。復調ロックやTSID読み戻しは得られてもhost TSが0バイトの試行が続いた。読み戻し値を受信TSのPATと同じ証拠にはしなかった。

複数試行後、元のBS4K設定へ戻しても純正HDMIが黒画面・選局失敗のままになった。HTTP4Kの取得が戻る場合でも純正decoderのreader接続が0/0で、視聴復帰とは言えなかった。利用者のコンセントリセットで復旧し、RAM上のツールを再投入して続けた。このHDMI復帰問題は最終版にも残る。

## 2. DEMUXへの経路を切り分け

serial/parallel、フレーム形式、TSIポート候補を比較したが、ロックだけではTSは出なかった。CPLDの`SetTsIn`をSoCクロスバー設定と仮定した経路も目的のAPIではなかった。

保存済みデータのloopbackを使うと、自分のDEMUX・ring・readerでTS/PATが読めることを確認できた。ただしloopbackの成功はアンテナからのライブ受信の成功ではない。

MEMORY DEMUXの対照は拒否され、LOCAL_DEMUX経路と実際のdriver要求を追った。論理入力0と1を物理0へ割り当てた比較から、通常BSでは物理TSI0→論理TSI1が必要と判明した。

## 3. descriptor解放の失敗と修正

初期readerはsize=0を空振りとしてcommitしなかった。このためclaimed descriptorが残り、teardownでdriver error1034になった。自分のring/readerだけを対象に回収を試みたが、解放できないものは保持し、他の純正リソースを推測で破壊しなかった。

size=0でも必ずcommitする修正後、短時間・15秒試験で追加残留なしを確認した。bootをまたいで古いアドレスを再利用して回収してはならない。

## 4. 放送波からの通常BS TS取得成功

SC1501A ISDB-S→物理TSI0→論理TSI1→type12 DEMUX→SYSTEM/TS ring→hostの経路で、BS朝日TSID0x4010を取得した。

15秒32,932,148バイト、188バイト同期・TEI・CC・PSI/SI CRC・PAT/PMTを独立解析した。別途PATだけの取得でもTSIDを照合した。[受信経路の詳細](BS2K-RECEPTION.ja.md)。

この時点ではスクランブルが残っており、TSが取れたことと映像デコード成功は分けて報告した。

## 5. CAS通信を特定

純正DESCRAMBLERデバイスの生成・初期configだけでは復号できなかった。card daemon、ICD queue、shared memory、既存flockの通信を追った。

従来カード向けINS34/P2=0では期待条件にならず、純正のcard type2分岐に沿ってP2=2へ変更。INS30/P2=2のパラメータとECM処理を使い、保存TSからMPEG-2/AAC映像音声をデコードできた。応答長・transport成功だけを復号成功とはしていない。

カード初期化・reset・新認証を行うのではなく、既存の稼働中経路を直列化した。鍵・カード番号・生応答は公開しない。[CAS実装の詳細](BS2K-CAS-INVESTIGATION.ja.md)。

## 6. ライブHTTPと共有broker

受信・section再組立て・ECM更新・MULTI2をHTTPのbackendへ統合。120秒ライブ復号、同一TSへの複数接続共有、別TS同時要求の拒否、2K→4KHTTP切替を確認した。

起動順の誤り、空ring、subscriber解放、REMUXプログラムの終了識別も修正した。生TSで同期だけ正常でもAVが使えなければ成功とは扱わない。最終的にもHDMI視聴の復帰は別問題として残した。

## 7. 六局への拡大

局表の古いNHK TSIDを流用して失敗したため、受信TMCCと放送メタデータで確認した値へ修正した。BS朝日、BS-TBS、BSテレ東、BS日テレ、BSフジ、NHK BSを個別選局し主映像・音声を実デコードした。

ECM到着前の先行パケットや更新の処理を見直した。BS日テレではPMTで関連を確定できないPID0x248が残り、未知PIDへ同じ鍵を当てたりSC flagだけを落としたりせず暗号化状態を保持した。

## 8. HDD保存とRAM不足

成果・復旧用ファイルを録画用HDDへ保存した。大きなarchiveを一旦tmpfsへ作るとRAMを圧迫し、UI異常・応答不良になった。この経路は中止し、直接HDDへ保存する方法へ変更した。

実験中には本体のHTTP/telnet/pingがすべて届かなくなるケースもあった。緑LEDを通信正常の証拠にせず、取得済みログを保持して電源リセット後に復旧を確認した。根本原因を完全解明したものではない。

## 9. EPGStation連携

既存4KのEPGプロキシへ通常BSのEIT collectorを追加。network4と11を区別してcacheを併合し、既存の番組表UIから予約・録画・ブラウザ再生を確認した。

途中では番組表APIの必須引数不足で400、aribtsのstream API取り違え、DBファイル名誤認、ブラウザ初期待機の不足があった。空DB作成物は除去し、実DBは正しいSQLite backupで保全した。既存予約を試験用予約と混同して削除しなかった。

最初のブラウザ試験が失敗したことも残し、MP4変換と実際のvideo進行を後の再試験で確認した。音声のdecoder成功は聴取試験とは区別した。

## 10. 自動再投入

旧watcherは固定4K版とHDMI decoder threadを正常条件にしていたため、統合版とheadlessな2K運用に合わせて変更。正常APIへの上書き禁止、残存自分プロセスの強制kill禁止、録画・scanner保護、boot・RAM・hash確認、共通flock、backoffを追加した。

idleな自分のサーバとRAMファイルを除去した後の再投入は成功。ただしコンセントOFF/ONから全経路を通す総合試験は未完了。TCPの一時設定による到達性問題にも対処したが、長期の完全自動運用成功とは主張しない。

## 11. 連続予約失敗と二段階の修正

最初の2K→4K試験では、MH-SDTが古く残るのでMPTで確認する方法に変更し、NHK BSP4Kへの切替を確認した。しかし日テレ・TBSの実予約が失敗し、MPTも古いまま残ると判明した。午前の結果を全4K局へ一般化した判断を訂正した。

最終版は純正ADSB sessionの要求と取得済みSID/NID、busy、RF/TSIDを照合し、新しい映像・音声リングを待つ。要求値だけ先行して変わる期間を完了と誤認しない。

2K→日テレ4Kと2K→TBS4Kの間隔0秒予約を自動終了まで確認し、各約280MBの4Kファイルを実デコード。番組表からの4K予約とブラウザ再生、NHK HTTP回帰も確認した。最初の並列再生タイムアウトは直列再試験で成功したが原因の断定はしない。[修正と数値](EPGSTATION-OTHER-4K-TRANSITION-20261016.ja.md)。

## 最終的な到達点と残課題

通常BS6局の主AV、120秒ライブ、共有・排他、EPG予約・再生、再投入、2K後の複数4K局録画を確認した。一方、HDMI復帰、日テレ一部PID、CS、長時間安定性、完全な電源断復旧、番組延長追従は未完了。隣接予約で前番組末尾が短くなる単一チューナー制約も残る。

本公開版は実証した受信処理を保ち、私的な51コミットの履歴は公開せず、本家の履歴から安全な差分として追加する。生の実験ログやメディアではなく、再現に必要な設定・実装と判断過程を公開する。

## 原本との再照合で補完した失敗条件・数値（2026-10-17）

初版公開の要約だけで、当時の全条件を否定済み/全品質を検証済みと読める部分を補う。以下は新しい実機試験ではなく非公開原本との照合。数値は異なる段階の標本を混ぜない。局別・切替別の一覧は[匿名検証マトリクス](VALIDATION-MATRIX.ja.md)。

### HDDの構成と最初の判断

500GB級HDDの既存構成は、通常ファイル用XFS領域と別のrealtime領域だった。FAT解釈の失敗を未初期化と決めつけず、realtime deviceを独立filesystemとして扱わなかった。利用者から初期化許可はあったが、既存構成で保存・hash照合・解除できたため初期化しなかった。媒体serialや個別mount名は公開しない。通常領域約4GiBの表示をHDD全容量と取り違えなかった。

### 復調からTS取得まで: どこまで否定できたか

| 試した条件 | 原本にある結果/訂正 |
| --- | --- |
| TSI0/1と188B serial、clock edge×VALID、SYNC有無 | 初期の実施組合せは0B。DEMUX論理入力まで全組合せを網羅したものではない |
| bank0の16=00/20/21、cc等、TLV/SPI forwarding候補、bank7 | 限定した変更はfull TS/PATとも0B。変更前へ戻した。bit名の推定を実証設定としない |
| SC/SoCのparallel整合、vendor base framing | 試した条件では0B。配線不在の証明ではない |
| TS_RECODER、PID0/sectionだけ | 初期入力経路では0B |
| 固定snapshot番地 | 実機tuner buildと0xa0のずれがあった。全0の内部状態という観測を撤回。build-id/参照命令を確認し、system13→1→13等を再観測 |
| FEM msg0x200d/20B経由 | 2秒待ちでは未lock、8秒でlock。ただし該当TSI組合せではTS0Bのまま |
| TSID選択レジスタ2f/30/31 | 40/10/00の要求反映。要求の読み戻しであって受信TS取得とは別 |
| 実受信TMCCを2回取得 | 相対TS0/1/2に4010/4011/4012、各16slot、合計48。40B本体も一致。復調の証拠だがTS取得ではない |
| TSID指定と相対TS0（31=00/08） | TSI0/1と合わせた4条件で0B。選択方法だけでは解決しない |

0B終了をスクリプト異常終了にして後半条件を実施しなかった回と、修正版で実施した回を区別した。空集合all()で既知packet一致trueと出す表示も非空条件へ修正した。「ソフトウェアの仮説はすべて否定した」という以前の断定は維持しない。

### 正の対照・descriptor・独立した4K終了不具合

- CPUリングへ合成TSを置いて12,408B一致。type12のmemory DEMUX仮説は1023で拒否された。この段階はDEMUX入力成功ではない。
- descriptorを整えた保存TS→LOCAL_DEMUXは1,540,096B全一致。timestamp付きTTSも4B除去後に同量一致、PATは112B/7 sections/CRC正常。追加pipeline_startは1001で拒否され、適用済み比較に数えなかった。
- 物理0→論理1の最初の試験は51,888B/276 packets取得後に1023/1034。size0 descriptorの返却修正後は2秒4,345,808B、PAT専用588B/21個、15秒32,932,148Bを正常終了した。
- 15秒の初受信は175,171 packets、PAT151個、PMT453個、完結PSI/SI1,690個CRC正常。論理割当とcrossbar各変更の単独効果は分離していない。
- 4Kのremove_streamで1042が出た独立不具合は、第3引数をflag=1と誤認したため。追加時と同じservice_idへ修正して解消した。HDMI問題まで解消した証拠にはしない。
- 通常BS同調だけ/TSI未変更でも黒画面を再現したため、TSI変更は必須条件ではない。reader0だけでTV停止を断定し、利用者の「映ったまま」という実表示確認で訂正した回もある。

### 保存TS・ライブ復号の実測と警告

初回保存TS復号は32,932,148B、175,171 packets中158,361 packetsを復号、8種のECMを処理、PES開始962個を確認した。合成MULTI2参照ベクトル9長と照合し、MPEG-2 1440×1080の10秒279frames、AAC48kHz stereo709framesをdecodeしたが、音声冒頭/EOFに2個のerrorが残った。

CA_PID1FFFをECM待ち対象にして約4MiBで止まったため除外。初期の単一ECMドメインでPMT外PID4E0/4E1を扱った方法は、6局拡大後に条件を厳しくし、全PMTが揃わない時の未知PIDへ鍵を流用しない方式へ改めた。

30秒65,798,120B/349,990 packetsと120秒261,554,060B/1,391,245 packetsは別標本。120秒はECM63更新、115秒3,430framesをdecodeし、cleanup/TSI復元成功。TEI/CC/完結CRC異常0でも音声境界error1個（25秒decodeでは3個）が残る。HTTP末尾の24/116B断片を別保存し、完結188B packetで解析した。全フレーム無警告ではない。

120秒中の別接続検査は通信timeoutした。共有200/競合503の成功根拠は30秒試験であり、120秒の同時接続試験成功とは書かない。初回の全通信不通も、同じbootで復帰し2Kソース作成前のログだったため、受信コードによるhangと断定しない。

### 六局拡大の二段階修正

ECM待ちを観測済み暗号化PIDへ絞るだけでは、全PMT待ちが残るためTBS/日テレの503は直らなかった。要求サービスのPAT/PMT整合を確認して開始する方式へ進めた。NHKの40F1は以前の0B結果をsentinel扱いした誤りで、放送NIT確認により解除した。

最終6局は各15秒/10秒AV decode成功。日テレはPID584/0x248の1,519 packetsを暗号化のまま保持し、残り174,870 packetsはSC0。全多重の復号成功とはしない。局表ID分離と各取得量は検証表に保持する。

### EPG・watchの実測と判断の修正

- 60秒130,941,060Bから766番組。内訳NHK116、日テレ132、朝日146、TBS122、テレ東122、フジ128。通常BS6局＋4K8局の番組表を観測したが完全な1週間を保証しない。
- 通常BS30分/4K2時間の収集周期と、EPGStationの取り込み周期は別。設定10分を実反映10分と言った説明を訂正し、イベント未対応fallbackでは約15分＋処理時間となる場合を記録した。
- 実行中の利用者録画がある間はwatchを更新しても旧mkraを停止しなかった。後で約2.18GBのファイルを確認したが、表示上の29分全区間の品質検証と呼ばなかった。
- idleサーバ不在・RAM配置先なしから転送/起動/経路確認まで約107秒、外部host peak19MiB。さらに2回監視して同じPID・1プロセスを確認。復元後6局各10秒、AV約9.15〜9.22秒、4K5秒24,969,032B/2秒100framesも確認。
- 同一bootでの試験なのでcold boot通し試験成功とはしない。旧4K専用865,932B、6局統合980,508B、午前修正983,268B、最終984,708Bを混同せず、公開最終版は検証表のSHA-256で特定する。
- tcp_tw_recycleの一時変更がguardに拒否され、転送後に起動できない失敗があった。完全一致1コマンドだけを許可し、16件のwatcher/guard試験で確認した。guard全体やfirewallを無効化したわけではない。

### 4K予約修正が段階的だったこと

午前にはMH-SDT不一致→MPT＋SI ring照合案→MPT＋新規ES方式と進んだ。ring案は503を再現して撤回。MPT＋ESはNHKの30秒間隔/間隔0秒で成功したが、夜の日テレ/TBS実予約でMPT本体/Cloneも古いと分かり、最終の取得済みADSB session方式へ変更した。午前の「最終方式」という原本見出しは当時の意味であり、現行の最終方式ではない。

午前代表4K214,318,872B/72.177556秒はAV10秒600frames成功だが、参照frame・PES境界・DTS警告があった。10bit HEVCをBaselineに渡すブラウザ変換は失敗し、6設定へyuv420pを追加して成功。時刻指定待機の古い時刻再利用は約5秒の遅延を生み、現在時刻で再計算して開始差約0.404秒に改善した。前の2Kが短縮・2ファイル分割になった例も残す。

定期2K EIT収集が約57秒でearly stream EOFになった例は旧cache保持で終了し、原因解消済みとはしていない。夜の最終4K録画・番組表操作は検証表K05〜K09の通り。約30秒で試験予約を終了した結果を番組全体の自然終了とは呼ばない。
