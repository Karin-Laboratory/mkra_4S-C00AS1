# BS2K / BS4K統合版の制限と証拠の範囲

2026-10-15〜16日の実測と公開ソースを区別する。`[M]`実測、`[S]`ソース/静的解析、`[U]`未検証。[検証マトリクス](VALIDATION-MATRIX.ja.md)に標本長・失敗・警告をまとめる。

## 受信できるもの・未検証のもの

通常BS6局の主映像・音声、BS2K120秒ライブ、2Kから複数4K局へのHTTP/予約録画切替は実測済み。[M] 通常BSのTS取得を「不可能」とした以前の説明は現在には当てはまらない。

| 項目 | 現在の状態 |
| --- | --- |
| 通常BS | NHK BS・BS日テレ・BS朝日・BS-TBS・BSテレ東・BSフジ主サービスを実測。朝日152/153のPAT/PMT確認を主サービスと同じAV試験には数えない |
| BS4K | 本家REMUXを維持。2K後のNHK BSP4K・日テレ4K・TBS4K切替を実測。内蔵局表全件の検証ではない |
| BS日テレ | 主AVはデコード成功。PID0x248の暗号化は残る。全多重の完全復号ではない |
| CS・advanced CS・BS8K・他サービス | 未検証/受信保証なし。局表に載ることは対応実証ではない |
| 地上デジタル | 有効なTS・AV取得は未実証。RFラッチ一致と復調ロックは別。BS経路の成功から地デジ成功を推定しない |
| 他機種・異なる純正版 | 固定ABI・ハッシュガードがあり未検証。類似機種の同一動作を保証しない |

## 物理チューナーは1基

同じTSキーは1つの受信ソースを共有する。異なるTS/BS4Kサービスへの同時要求は503。priorityは情報として扱い、高優先度要求による強制横取りは行わない。[S]

最後のクライアント終了後も約3秒のlingerがある。瞬間的に503になり、EPGStationの再試行で成功した実測がある。録画開始遅延や番組末尾短縮を完全には防がない。[M] `allowEndLack=true`の連続予約では先行録画が約15秒短縮され、一度は再試行で2ファイルに分かれた。隣接する両番組の全編保存を保証しない。

## HDMI・待機状態

BS2Kへの同調後に純正HDMIが黒画面となり、リモコンの局変更・赤緑切替だけでは戻らないケースがある。**HDMIの確実なソフト復帰は未解決。** TSI復元、4KのES生成、HTTP配信、テレビ実表示は別の確認項目。[M]

純正視聴を止めないという本家4K経路の説明を、BS2K切替にも適用してはいけない。自動起床も保証しない。緑LEDだけでは映像・通信正常の証拠にならず、スタンバイでは必要なESリングや純正機能が使えない場合がある。[M]

## CAS・TS品質

BS4Kでは純正で復号したESをREMUXする。BS2Kではmkraが内蔵CASと通信しCPUでMULTI2復号する。実鍵・カード番号・生応答は配布/記録しない。[S]

受信TSは多重全体で、サービス別の完全なPID分離を保証しない。未知PIDの鍵を推測せず、暗号文とscrambling flagを維持する場合がある。CASの曖昧なtimeoutでは再送せずlatched状態で停止する。[S]

120秒標本はTEI/CC/完結section CRC異常0だったが、音声の開始・終了境界にdecode error1個が残った。25秒decodeでは3個、初回保存TS復号では2個。HTTP終了で切れた末尾24/116バイトは別保存して完結188バイトpacketを解析した。全編・全フレーム無警告や長時間安定運用は未実証。[M][U]

## EPG・録画・運用

- BS4KのMMT-SIは`--epg-dir`または`--epg-tap`で取得。通常BSのH-EITは別ホストのcollector→proxyで提供し、本体APIが直接2K番組表を収集するわけではない。
- `/api/status`の`epg.storedEvents`は本体側では0の互換placeholder。番組がないとの判定には実際の`/api/programs`を使う。[S]
- `/events`は未実装。収集30分/2時間とは別にEPGStation取り込みの遅延がある。開発時の設定10分に対し、イベント不通時は約15分＋処理時間となる場合があった。[S][M]
- 番組ID配信の終了はcacheの時刻snapshotに基づく。延長・時刻変更への継続追従は未完了。
- EPG巡回は録画と同じチューナーを使う。共通flockと予約接近guardでも、即時録画との競合を完全には防げない。
- RAMの空きとCPUに余裕が必要。大きいTS/archiveを本体/tmpへ保存してOOMで純正UIとmkraが終了した実例がある。外部保存を使う。
- RAM再投入はサーバ不在・配置先なしから約107秒の復元を実測。コンセントOFF/ON・LAN復帰・予約開始までの通し試験は未完了。既存mkraの異常を強制killして直す設計ではない。
- 認証/TLS・完全なMirakurun機能互換は提供しない。`/api/version`の3.9.0は互換表示であり全API実装の宣言ではない。

## 調査用コマンドを日常運用に使わない

統合サーバの通常起動は`serve --remux4k --tune --bs2k`。`--bs2k`には両flagが必要で、`--file`、`--test-pattern`、`--raw-stream`、idle-sleepとは併用しない。

`gr`、`gr-off`、`demux`、`tsrec`、`dmd-*`、`isdbs-*`、`fem-dev`等は調査用で、I2C・TSI・純正受信状態を変更し得る。`probe --scan`の無効handle試行ではkernel oopsの実例がある。復旧手順として無作為に実行しない。read-only観測でも固定版の適合を確認する。

## 過去の否定結果と訂正

[本家由来の説明を履歴として保存](history/BASELINE-LIMITATIONS.md)。当時TSI0/1や電気設定を変えて0バイトだった事実は削除しない。ただし物理入力だけを切り替えてDEMUX論理入力0を維持した比較もあり、全組合せの否定ではなかった。

後に「物理TSI0→論理TSI1へ割当」と「DEMUXも論理1」の組合せで取得した。したがって「配線がない」「ソフトでは不可能」「同じ出口なので地デジも不可能」という断定は撤回。個別bitの意味や論理/crossbar各変更の単独効果までは分離できていない。

確認・復旧は[運用トラブル対応](TROUBLESHOOTING.ja.md)。
